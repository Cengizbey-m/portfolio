# Feather (Capstone, Team of 4)

**Live:** [feathertrade.org](https://www.feathertrade.org/)

## Result

Feather was selected for the final showcase round and judged **first overall out of more
than fifty capstone projects** at Sheridan's 2026 showcase. It was graded **97/100** in the
final term, up from 94/100 at the prototype stage.

This is the biggest thing I have built with other people. It ran across two terms and a
full academic year, with four developers coordinating design decisions, scope, and a
codebase that had to survive all of it.

## Summary

Feather forecasts next-day stock movement and, more importantly, shows you how much to
trust the forecast. Most student prediction demos print a confident number and hide the
error rate. We built the opposite: every prediction ships with the evaluation evidence
behind it.

## The problem

A model that is right 55% of the time and a model that is right 80% of the time look
identical in a UI that only shows a prediction. That is not a visualization problem, it is
an honesty problem. If a user cannot see how a model performs against a naive baseline,
the interface is quietly lying to them.

## What I owned

I worked on the evaluation layer and the boundary between the Python service and the React
client.

**Evaluation.** I built the layer that scores every model run against baselines, including
a naive "tomorrow looks like today" predictor. If a trained model cannot beat that, the UI
says so. This became the feature judges asked about most, because it is the part that
makes the product defensible rather than impressive.

**The API contract.** I defined and implemented the interface between the FastAPI model
service and the React frontend. Fixing the shape of that contract early meant the frontend
team could build against a stable spec while the model work was still changing underneath,
so neither half of the team sat blocked on the other.

**Containerization.** Docker for the service, so four people ran an identical environment
and demo day did not depend on whose laptop was being used.

## Tech

- Frontend: React + TypeScript (Vite)
- Backend: FastAPI (Python), SQLAlchemy
- Models: scikit-learn baselines (SVR, Random Forest)
- Docker for local and demo environments
- Deployed on Vercel

## What a year teaches you

The evaluation layer was built after the models, which meant a round of rework once we
could actually see how weak some early results were. Next time I would build the scoring
harness first and develop the models against it, the same way you would write the test
before the implementation.

The other lesson was less technical. Over two terms, the thing that cost the most time was
not code, it was decisions left ambiguous. The stretches where we moved fastest were the
ones where somebody wrote the decision down.
